# daily-summary

今日の学習セッションをまとめて学習メモに記録し、GitHubへpushするskill。

## いつ起動するか

- ユーザーが以下のような発言をした時:
  - 「今日のまとめ」「今日はここまで」「終わりにする」
  - 「区切る」「セーブして」「保存して」
  - 「pushして」「コミットして」
- 学習セッション終了の合図があった時

## 動作手順

### 1. 今日の対話を振り返る

このセッション中に発生した以下を洗い出す：
- 学んだ概念・知識
- ユーザーが投げた質問とその解消状況
- 躓いたポイント、気付き、誤解の発見
- 実装した内容（コードがあれば）

特に **`learning-memo` skill でまだ記録されていない事項** を意識する。

### 2. 現在のフェーズを特定

- `roadmap/README.md` の「## 現在のフェーズ」を読む
- 該当の `roadmap/{NN}-{name}-notes.md` を開く（Read）

### 3. 当日セクションへ追記

- 今日の日付セクション（`## YYYY-MM-DD`）を確認 / 作成
- 以下のカテゴリへ追記:
  - **学んだこと**: 新しく理解した概念
  - **質問・疑問**: 投げた質問（解消したものは「(解消)」と記載）
  - **理解度メモ**: 躓いたポイント、誤解、深い理解の所感
  - **実装したこと**: コードを書いた場合、実装内容とハマりポイント
- 既存内容は **絶対に壊さない**（Read してから Edit）
- 末尾に **その日の総括** を1〜2行で書いてもよい

### 4. TODOチェックボックスの更新

- 該当フェーズの `roadmap/{NN}-{name}-todo.md` を Read
- 今日の学習・実装で完了した項目があれば `[ ]` → `[x]` に更新する
- 判断基準:
  - 概念を理解して説明できる状態になった
  - コードを書いて動かした
  - 練習問題を解いた
- 既存のチェック状態は壊さない（Read してから Edit）
- 完了が部分的な場合は無理にチェックを入れず、ユーザーに確認するか保留

### 5. 変更内容を確認

```bash
git status
git diff --stat
```

### 6. コミット & push

#### gh アカウントの確認
事前に `gh auth status` で active account が `Akamine2001` であることを確認。
違っていたら `gh auth switch -u Akamine2001`。

#### add
- 具体的なファイル名で `git add` する（`git add .` は避ける）
- 機密ファイル（`.env`、トークン等）が含まれていないか確認

#### commit
日本語で意味のあるコミットメッセージを書く。`git commit -m` のヒアドキュメント形式を使う：

```bash
git commit -m "$(cat <<'EOF'
<フェーズ or トピック>: <学習・実装内容を簡潔に>

<必要なら詳細を箇条書き>

🤖 Generated with [Claude Code](https://claude.com/claude-code)

Co-Authored-By: Claude Opus 4.7 (1M context) <noreply@anthropic.com>
EOF
)"
```

例:
- `フェーズ1: 所有権と借用の学習`
- `フェーズ2: clap導入とaddコマンド実装`
- `ロードマップとskill初期セットアップ`

#### push

```bash
git push
```

### 7. ユーザーへ報告

短くサマリ:
- 何を notes に追記したか
- 何をコミットしたか
- pushが成功したか
- リポジトリURL（必要なら）

## 重要なルール

1. **既存メモを壊さない**: notes ファイルは必ず Read してから追記
2. **secretsを含めない**: `.env`, APIキー, トークン等は絶対にコミットしない（`.gitignore` で除外済みだが念のため確認）
3. **コミットメッセージは日本語・具体的**: 「update」「fix」だけは避け、何を学んだか / 実装したかが分かるものに
4. **アカウント確認**: gh active account が `Akamine2001` であることを必要に応じて確認
5. **push失敗時の対応**: 認証エラーや conflict があれば原因を確認し、ユーザーに報告
6. **destructive な操作はしない**: `git reset --hard`, `git push --force` は使わない
