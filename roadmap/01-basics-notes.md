## 2026-05-05

### 学んだこと
- `cargo new <name>` で最小構成のRustプロジェクトを生成できる（`Cargo.toml` + `src/main.rs`）
- `Cargo.toml` はプロジェクトの設定ファイル。Pythonの `pyproject.toml` 相当。`[dependencies]` セクションに外部ライブラリを書く
- `fn main()` がプログラムの開始地点。Pythonの `if __name__ == "__main__":` に相当するが、Rustでは必須・明示的
- `println!` の末尾の `!` は「マクロ呼び出し」の印。普通の関数ではない（詳細は後で）
- `cargo run` は内部で「コンパイル → 実行」の2ステップを実行している
- 実行ファイルは `target/debug/<プロジェクト名>` に生成される。これだけで配布可能（Rust未インストール環境でも動く）
- Rustはコンパイル言語、Pythonはインタプリタ言語。Rustは事前に機械語に変換してから実行する
- macOS/Linuxでは実行ファイルに拡張子はつかない（実行権限ビット `x` で判別）。Windowsでは `.exe` がつく

### 質問・疑問
- 実行ファイル（`target/debug/hello-world`）に拡張子がないのはなぜか？
  → macOS/Linuxは「実行権限ビット」で実行可能かを判別するため拡張子不要。Windowsだと `.exe` がつく
- ビルドしたバイナリは他のOSでも動くのか？
  → 動かない。バイナリは「OS × CPUアーキテクチャ」のターゲットに依存する（例: macOS-arm64用に作ったらWindowsやLinuxでは動かない）
  → 別OS向けに作りたい場合は **クロスコンパイル**（`rustup target add` + `cargo build --target ...`）。実務ではCI（GitHub Actionsなど）でOSごとに並列ビルドするのが一般的
  → 配布物の特性比較: Python = ソース1つ + ランタイム必須、Rust = OS/CPUごとにバイナリ必要だが実行時依存ゼロ
- 配布時はターゲット指定でビルドしてその成果物を配るのか？
  → 基本はその通り。配布パターンは3つ：
    1. ビルド済みバイナリを配る（GitHub Releases に各OS向けに置く。`ripgrep`, `bat`, `fd` などRust製CLIで定番）
    2. `cargo install <crate>` でソース配布 → ユーザー側でビルド（Rust環境必須）
    3. パッケージマネージャ経由（`brew install`, `apt install`, `scoop install` など）
  → 配布時は **リリースビルド**（`cargo build --release`）を使う。`target/release/` に最適化されたバイナリが出る
  → デバッグビルド vs リリースビルド: コンパイル時間（速⇔遅）、実行速度（遅⇔速）、サイズ（大⇔小）、デバッグ情報（有⇔無）。開発中はdebug、配布・本番はreleaseが鉄則
  → 実務ではGitHub ActionsでOS別runnerに並列ビルドさせて、成果物をGitHub Releasesにアップロードするのが定番フロー

### 理解度メモ
- 「コンパイルしてバイナリを作る」感覚をPythonにはない初体験として実感した
- `cargo run` でビルド成果物が `target/` に残ることを確認

## 2026-05-06

### 学んだこと
- `let` で変数宣言する。Pythonの `x = 5` と違い、`let` キーワードが必須
- `println!` のプレースホルダ `{}` は順番に第2引数以降の値が埋め込まれる
- 派生形:
  - 位置指定 `{0}` `{1}` で同じ値を複数回使える
  - 名前付き `{name}` + `name = "太郎"` で読みやすく
  - **f-string風 `{x}`（edition 2021以降推奨）**: スコープ内の変数を直接埋め込める。ただし式は書けない（`{x + 1}` はNG）。Pythonと違うポイント
- `{` `}` をリテラルとして出力したい場合は **`{{` `}}` でエスケープ**（Pythonのf-stringと完全に同じ規則）

### 質問・疑問
- `println!` で引数が2つ以上ある場合は？ → `{}` を並べて第2引数以降を順番に書く。位置指定・名前付き・f-string風の3バリエーションあり
- f-string風で `{x}` を文字列リテラルとして書きたい場合は？ → `{{x}}` とエスケープ

### 理解度メモ
- フォーマット文字列構文はPythonと近い感覚。違いは「式が書けない」点だけ意識すれば良さそう
- Rustの変数は **デフォルトで不変（イミュータブル）**。変えたい時だけ `mut` をつける思想
- Pythonとの対比: Pythonは何でも再代入OK、Rustは「変えるなら明示しろ」のスタンス
- TypeScriptの `const` / `let` との対比:
  - TS `const` ↔ Rust `let`（再代入不可）
  - TS `let` ↔ Rust `let mut`（再代入可）
  - ただし不変性の深さが違う: TSの `const` は **浅い**（オブジェクトのプロパティは変えられる）、Rustの `let` は **深い**（中身まで変えられない、`mut` で初めて中身も変更可）
- Rustのコンパイルエラーは非常に親切（エラー番号 + 問題箇所 + 修正候補までセットで表示）。エラーを読むスキル自体が学習に直結する
- **シャドーイング**: `let` で同じ名前の変数を何度でも再宣言できる。「再代入」ではなく「新しい変数を作って前のを覆い隠す」
  - `mut` 不要、型も変えられる
  - 例: `let s = "  42  "; let s = s.trim(); let s: i32 = s.parse()?;`（&str → &str → i32）
- **シャドーイング vs `let mut`**:
  - `let mut`: 同じ変数の中身を書き換え（型は固定）
  - シャドーイング: 新しい変数で覆い隠す（型変更可、不変性は保たれる）
- **重要な誤解の解消**: シャドーイングは「Pythonのゆるさを真似るため」ではなく「`mut` を避けて不変性を保つため」に使う
  - 各時点で型はコンパイル時に厳密に確定する。Pythonのような実行時型エラーは起きない
  - Rust界隈では `let mut` より積極的に推奨される書き方
  - 頻出パターン: パース処理（`&str → i32` など）、値の正規化チェーン、意味付けの変更

### 質問・疑問（追加）
- シャドーイングってRustで実際に使われるのか？緩くなるのはRustの良さを消しているのでは？
  → 実際よく使われる。むしろ推奨される。`mut` を避けて不変性を保ちつつ値を変換できるため、Rustの思想（「変えるつもりがないなら不変にしておく」）と整合する
  → Pythonの「ゆるさ」とは本質的に違う。型は各時点でコンパイル時に確定し、間違いはコンパイル時に検出される
- 不変で宣言するほうがメモリも安全になるのか？
  → 半分正解、半分は別の話。**メモリ安全性は「所有権・借用・ライフタイム」が担っており、不変性自体ではない**
  → 不変性が貢献するのは「論理バグ予防」「並行処理の安全性（不変参照は複数スレッドから同時に読める）」「最適化」「可読性」
  → Rustの安全性は2段構え:
    1. **メモリ安全性** = 所有権システム（use-after-free, 二重解放, データ競合などをコンパイル時に防ぐ）
    2. **論理的な安全性** = 不変性デフォルト + 型システム
  → シャドーイングは間接的にメモリに優しい（古い値はアクセス不可になり、スコープを抜けると解放される）が、メモリ安全を「作っている」わけではない
- 不変参照とは？（プレビュー、トピック6で深掘り予定）
  → Rustでは値の使い方が3つに分かれる:
    1. **所有** (`let s = ...`) = 何でもできる
    2. **不変参照** (`&s`) = 読み取り専用で借りる。複数同時OK
    3. **可変参照** (`&mut s`) = 読み書きOK、同時に1つだけ
  → `&` で「借用」を表現する
  → Pythonには明示的な「参照を作る」概念はない（暗黙の参照共有）。Rustは「所有権を渡す」のか「借りる」のかを明示的に書き分ける
  → 不変参照は複数同時に存在できる = 並行処理で安全に共有できる、という話に繋がる
- そもそも「参照」自体はPythonにもあるのか？なぜRustは `&` を明示的に書く？
  → Pythonにも参照はある（変数は全部暗黙的な参照、`b = a` でリストを共有する挙動など）
  → Rustが `&` を明示するのは「**所有権を渡す**」のか「**貸す（参照）**」のかを書き分けるため
    - `some_func(s)` → 所有権を渡す（以後 `s` は使えない）
    - `some_func(&s)` → 貸すだけ（`s` はまだ使える）
  → コンパイル時にメモリ安全を保証するため、暗黙にできない（Pythonとの設計思想の差）
  → 詳しくは所有権トピックで
- 基本型のメモ:
  - 整数: `i8/i16/i32/i64/i128/isize`（signed） `u8/u16/u32/u64/u128/usize`（unsigned）。デフォルトは `i32`
    - `i` = integer、`u` = unsigned integer の略
  - 浮動小数点: stableは `f32`（単精度）と `f64`（倍精度）の2つだけ。デフォルトは `f64`。`f16`/`f128` はnightly only
  - 真偽値: `bool`（`true`/`false`、小文字。Pythonは大文字始まり）
  - 文字: `char` は 1文字（Unicode 4バイト）、シングルクォート `'あ'` で囲む
- `char` と文字列の区別:
  - `'あ'` → `char` 型
  - `"あ"` → `&str` 型（文字列）
  - `let e: char = "あ"` はコンパイルエラー（型不一致 `expected char, found &str`）
  - Pythonは「長さ1の文字列」を文字として扱う（`str` のみ）が、Rustは型レベルで明確に分けている
- `char` には複数文字は入らない。Rustの文字列型は別途2種類:
  - `&str`（文字列スライス、リテラルの型）: `let s: &str = "hello"`
  - `String`（所有権を持つ可変長文字列）: `let s: String = String::from("hello")`
  - PythonはすべてS `str` で済ませるが、Rustは用途で型を分けてメモリの扱いを明確化
- **型推論のデフォルト**:
  - 整数リテラル `let a = 5` → `i32`
  - 浮動小数点 `let b = 5.0` → `f64`
  - 文脈から型が決まる場合は推論が優先される（関数引数の型に合わせる、など）
  - リテラルに型サフィックスを付けられる: `5u8`, `3.14f32` など
  - 型を確認したいトリック: `let _: () = a;` のように `()` に代入しようとするとエラーメッセージに推論結果が出る
- **「符号」とは？** = プラス/マイナスの記号
  - signed (`i*`) = マイナスも扱える / unsigned (`u*`) = 0以上のみ
  - 同じビット数なら正の範囲が2倍になる（例: `i8` -128〜127 vs `u8` 0〜255）
  - 使い分け: 年齢・個数・長さ → `u`系、差分・座標・温度 → `i`系、迷ったら `i32`
  - Pythonの `int` は無限精度・符号区別なし。Rustは効率のためサイズと符号を決めて使う
- **「リテラル」とは？** = ソースコード中に直接書く値そのもの
  - `5` → 整数リテラル、`3.14` → 浮動小数点リテラル、`"hello"` → 文字列リテラル
- **リテラルに型サフィックス** をつけて型を明示できる
  - `5u8` = u8型の5、`5i64` = i64型の5、`3.14f32` = f32型の3.14
  - `let x: u8 = 5;` と `let x = 5u8;` は同じ意味
  - 関数引数で直接リテラルを渡すときに便利。実用上は `let x: 型` 形式の方が読みやすく、サフィックス版はあまり使われない
  - 文字列リテラルにはサフィックスはない（`&str` 固定）

## 2026-05-07

### 学んだこと
- **`&str` の正体**: 「ポインタ + 長さ」の **ファットポインタ**（fat pointer）。データ本体は静的領域（バイナリに埋め込み済）にあり、`&str` 自身は場所と長さだけを持つ
  - C言語のヌル終端と違い、長さを最初から持つので `len()` がO(1)、途中に `\0` を含められて安全
- **`String` の正体**: 「ポインタ + 長さ + 容量」の3要素。データ本体はヒープ。`s` 自身がデータを直接持つわけではなく、ヒープを指すポインタを持つ
  - **長さ (len)**: 今入っているバイト数 / **容量 (capacity)**: 確保している箱のサイズ
  - 空の `String::new()` は容量0でヒープを確保しない（遅延確保の最適化、ポインタは dangling な無効値）
  - `String::with_capacity(n)` で初期容量を予約できる（再確保を減らせる）
- **`String` の容量超え再確保**: `push_str` などで容量を超えると、新しい大きいヒープを確保 → コピー → 古いヒープを解放 → ポインタを更新。倍々戦略で **amortized O(1)**（Pythonの `list.append` と同じ仕組み）
- **`&str` と `String` の使い分け（関数引数）**:
  - 基本は **`&str` で受け取る**（柔軟・所有権を奪わない）
  - 理由1: `&String` は **Deref coercion** で `&str` に自動変換されるため、`&str` で受け取れば両方渡せる
  - 理由2: 所有権を奪わないので呼び出し元で後も使える
  - **`&String` で受け取るのは非推奨**（型として存在はするが、リテラルを渡すのに `.to_string()` が必要で柔軟性が落ちる）
  - 例外として `String` で受け取るのは「構造体のフィールドに保存」「加工して返す（ビルダー的）」など所有権が欲しいとき
- **`let mut s` と `&mut String` は別物**:
  - `let mut s: String` → 「**変数 s 自身が書き換え権限を持つ所有者**」
  - `&mut String` → 「**他の変数が所有している String を、書き換え権限つきで借りる型**」
  - 両者の `mut` は別の意味
- **借用には2種類**:
  - 不変参照 `&T`: 読むだけ。**同時に何個でも作れる**
  - 可変参照 `&mut T`: 書き換え可能。**同時に1個まで**
  - 不変参照と可変参照は **同時に存在できない**
- **`let mut s` でも `&s` で渡したら借りた先は読むだけ**:
  - 所有者の `mut` と、参照の `&`/`&mut` は2段階のチェック
  - 借りた側は「貸してもらった権限の範囲内」でしか操作できない
  - `let s`（mutなし）から `&mut s` を作ろうとするのはエラー（所有者が書き換え権限を持っていないため）
- **NLL（Non-Lexical Lifetimes）**:
  - 参照の生存期間 = **実際にコード上で使われる期間**（スコープ全体ではない）
  - コンパイラが「参照が最後に使われる位置」を静的解析で特定する
  - 「使い終わった参照」は数に入らないので、その後 `&mut` を作ってOK
  - **そもそも一度も使われない参照** なら、生存期間ゼロなので即 `&mut` を作れる（unused warningは出るがエラーにはならない）
- **借用ルールの本質**: 「不変参照と可変書き換えの **使用期間が重なる** とエラー」
  - 「参照を作ったらmutが作れない」ではなく、「使用期間が重ならないこと」が条件
- **借用チェッカが防ぐもの2種類**:
  - パターンA: ヒープ再確保で参照先が消える（dangling pointer）
  - パターンB: 読んでる最中に中身が書き換わる（データ競合、特にマルチスレッド）
- **引数で `&mut String` を使うメリット**:
  1. 呼び出し側のコードがシンプル（シャドーイングで受け取り直し不要）
  2. ループ内で自然に使える（所有権の往復が要らない）
  3. 複数の関数で同じバッファを書き換えられる（ログバッファ等）
  4. 構造体のメソッド（`&mut self`）でほぼ必須
  5. 不要なムーブを省略できる
- **メモリ操作のコスト感**:
  - スタック上のポインタ書き換え: 数ナノ秒
  - ヒープ確保 (`malloc` 相当): 数百ナノ秒〜マイクロ秒
  - 100〜1000倍くらい差がある。ホットループで再確保が頻発すると無視できない
  - **`&str` の貼り替えはタダ同然、`String` の操作は容量内ならほぼタダ、再確保が走ると重い**

### 質問・疑問
- `let mut s: &str` と `String` の違い → `mut` の効き方が違う。`&str` は「指す先を貼り替える」のみ、`String` は「中身を書き換える」もできる
- バッファ容量を超えた場合や新しいヒープ確保には時間がかかる？ → かかる。スタック操作の100〜1000倍。`with_capacity` で予約するのが定石
- `let mut s` で作った `s` を `&s` で借りた場合、借りた先で編集できる？ → できない。`&s` は不変参照なので読むだけ
- 参照が使われていないなら mut で書き換えても問題ない？ → 完全に正しい。NLLでそう判定される
- 使わなくても mut の可変参照は作れる？ → 作れる（ただし不変参照を以降使わないという条件）

### 理解度メモ
- **「所有権」の感覚を掴んだ**: 「データ本体に対する責任と権限のセット」「参照ではなく、データ本体に直結する関係」と理解
- 所有権の細かい権限はトピック6で深掘りする予定。今は概念レベルの理解で十分
- **`mut` が2箇所に出てくる問題** が混乱の原因だったが、「所有者自身の権限」と「借りる側に渡す権限」の2段階チェックと整理すると腹落ちした
- **NLLの判定基準**: 「使い終わるまで待つ」のではなく「使用期間が重ならない」。ユーザーが直感的に「使ってないなら関係ないだろ」と言ったのは正しく、Rustチームも2018年にそう改善した（NLL導入）
- **借用チェッカが何を守っているか** が腹落ちした: dangling pointerとデータ競合の両方をコンパイル時に防ぐ
- 引数の使い分けの判断軸: 「読むだけ → `&str`」「所有権が欲しい → `String`」「書き換えたいが所有権は奪いたくない → `&mut String`」

### 実装したこと
- `practice/string-practice/` を作成し、3パターンの関数を実装して動作確認
  - `print_length(s: &str)` → 不変参照で読むだけ。`String` を `&s` で渡しても自動変換（Deref coercion）で受けられた
  - `add_prefix(s: &mut String)` → 可変参照で受け取り `insert_str` で書き換え
  - `append_word(s: String)` → 所有権を奪う版
- ハマりポイント: `String::insert` は **char専用**。`&str` を挿入したいなら `insert_str` を使う必要がある。また `insert_str` は `&mut self` を要求するので関数引数を `mut s: String` にする必要がある
- **所有権ムーブをコンパイル時に体感**: `append_word(s)` の後に `println!("{}", s)` を書こうとするとエラー（`borrow of moved value`）。エラーメッセージが「いつムーブして、いつ使おうとしたか」を行番号付きで指摘してくれて非常に親切
- `let mut s = s;` で関数内シャドーイングして `mut` 化する書き方も試したが、関数引数自体に `mut` を付ける（`fn append_word(mut s: String)`）方がシンプル
